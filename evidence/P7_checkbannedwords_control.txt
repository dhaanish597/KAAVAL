P7 — checkBannedWords positive control: proof it can fail
=========================================================

Decision 88 says every guard in this project needs one run where it fails on
purpose, because a check that has only ever been green is indistinguishable
from a check that cannot go red. This file is that run for checkBannedWords.

checkBannedWords was already known-live in one direction: planting
`// negative control: risk` in app/src/main/java/app/vaakku/ui/CopyRes.kt made
it report 1 finding and exit 1 (file restored, git diff empty). So it does
fire on a banned word that is in front of it.

What it had no defence against was a banned word it never looked at. The task
walks a fixed list of source roots; "0 findings" is the same output for
"nothing is wrong" and "nothing was read". Move a source root, rename a source
set, or add a source file extension the filter does not list, and the guard
stays green while scanning less and less of the app.

WHY PER ROOT AND NOT A TOTAL FILE COUNT
---------------------------------------
The first attempt at this control was a floor on the total number of files
scanned: minimumFiles = 40, against 100 in a healthy tree. IT DID NOT WORK,
and the way it failed is the whole reason the per-root form exists.

Simulating a moved app/src/main/java — 46 files, every Kotlin UI string in
the app, i.e. precisely the files most likely to carry a verdict-flavoured
string — left 54 files behind. 54 > 40, so the guard printed:

    checkBannedWords: clean (54 files scanned, 0 findings).
    BUILD SUCCESSFUL
    EXIT: 0

A total floor high enough to catch that would have to sit above 54, which is
within ordinary churn of 100 and would fire on any normal refactor. So the
control is now per root: every declared root must still exist, and every root
must contribute at least one scannable file. That 54 is visible in RUN 2
below — the five surviving roots sum to exactly it.

The check is also deliberately split into declaredScanRoots() (the literal
list) and scanRoots() (existence-filtered), so the guard can tell "this root
is deliberately absent" from "this root moved and nobody noticed". Before the
split there was only the filtered list, and a vanished root was silently
dropped.

HEALTHY PER-ROOT COUNTS, FOR FUTURE REFERENCE
---------------------------------------------
Measured at commit 1921593, with no uncommitted source files present.

    app/src/main/res                   8
    app/src/main/java                 46
    app/src/debug                      9
    app/src/main/AndroidManifest.xml   1
    domain/src/main                   29
    tools/packet-cli                   7
                                     ---
                                     100

These numbers WILL drift as the project grows, and drifting upward is not a
problem — the check has no upper bound and no total floor, precisely so that
ordinary growth never has to touch it. Each number is a per-root floor of 1 in
practice; the table is here to make a *collapse* recognisable, not to be
matched exactly. (Already drifting: a new `domain/.../TamilByteRepair.kt` was
in the tree as untracked work while this was written, and the scan read 101
files, clean. domain/src/main becomes 30 when that lands.)

If a future run reports a materially smaller number for a root that still
exists, the fix is to find out where the files went — NOT to remove the root
from the list to make the build green. That instruction is also in the
comment above the check in build.gradle.kts, where someone tempted to do it
will actually be looking.

AFTER THE CONTROL
-----------------
build.gradle.kts restored from backup; `git diff` shows only the intended
positive-control addition (60 insertions, 4 deletions) and no trace of either
simulation; the java_MOVED path and the extra gradle/ root are both gone from
declaredScanRoots(); `git status --short` lists no stray files.

WHAT THIS DOES AND DOES NOT PROVE
---------------------------------
Proves: checkBannedWords fails when a banned word is present (tested
separately, CopyRes.kt), AND fails when part of the source tree silently stops
being read (both branches, above). It is live in both directions.

Does not prove: that the banned-word list itself is complete, or that the
extension filter covers every file type the app will ever use. The per-root
check makes a root going quiet loud; it cannot make a word that was never
banned illegal. The schema-guard test (§5.9) covers the field/class side and
has its own positive control (it asserts it found >= 20 classes) plus a
parameterized test-of-the-test on the banned pattern.
